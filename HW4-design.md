## 1. DDD: доменные зоны (ограниченные контексты)

```
┌──────────────────┐   ключ валиден?   ┌──────────────────┐  резерв (синхронно)  ┌──────────────────┐
│ 1. АККАУНТЫ      │◄──────────────────│ 2. СООБЩЕНИЯ     │─────────────────────►│ 4. БИЛЛИНГ       │
│    И ДОСТУП      │                   │                  │                      │                  │
└──────────────────┘                   └────────┬─────────┘                      └────────▲─────────┘
                                                │ MessageAccepted                         │
                                                ▼                                         │
                                       ┌──────────────────┐   MessageStatusChanged        │
                                       │ 3. ДОСТАВКА      │──────────────┬────────────────┘
                                       │ (провайдеры)     │              ▼
                                       └──────────────────┘     ┌──────────────────┐
                                                                │ 5. ВЕБХУКИ       │──► сервер клиента
                                                                └──────────────────┘
```

Зоны общаются **событиями** (подход EDA), а не лезут в базы друг друга. Синхронный вызов только один: резерв денег в Биллинге. Без денег мы не имеем права ответить клиенту `202 Accepted`.

### 1. Аккаунты и доступ (Identity)
Кто клиент и может ли он вызывать API. Сюда входят регистрация, подтверждение email и номера, выдача и отзыв API-ключей, переход из тестового режима в боевой.

| Термин | В коде | Определение |
|---|---|---|
| Аккаунт | `Account` | Компания-клиент SMSGate. Владеет балансом, ключами и сообщениями |
| Участник | `Member` | Человек с логином в кабинет аккаунта (разработчик, техлид, бухгалтер) |
| API-ключ | `ApiKey` | Секрет для вызова API. Бывает тестовым (`sk_test_`) и боевым (`sk_live_`). Хранится только хэш |
| Режим | `Mode` | `test` или `live`. Определяется ключом, а не настройкой аккаунта |
| Подтверждённый номер | `VerifiedPhone` | Номер участника, подтверждённый кодом. Только на него можно слать SMS тестовым ключом |

### 2. Сообщения (Messaging)
Ядро продукта. Принимает запрос, валидирует номер и текст, считает сегменты, обеспечивает идемпотентность, хранит сообщение и его итоговый статус.

| Термин | В коде | Определение |
|---|---|---|
| Сообщение | `Message` | Одно SMS одному получателю. Может состоять из нескольких сегментов |
| Получатель | `Recipient` | Номер в формате E.164 (`+79991234567`) |
| Сегмент | `Segment` | Часть SMS, которую оператор тарифицирует отдельно: 160/153 символа латиницы или 70/67 кириллицы |
| Кодировка | `Encoding` | `GSM7` (латиница) или `UCS2` (кириллица и эмодзи). От неё зависит длина сегмента |
| Ключ идемпотентности | `IdempotencyKey` | Строка от клиента. Повтор с тем же ключом в течение 24 часов возвращает исходный ответ |
| Статус сообщения | `MessageStatus` | `queued` → `sent` → `delivered` / `undelivered` / `rejected` |

### 3. Доставка (Delivery)
Как сообщение физически доходит до оператора. Здесь выбор провайдера, отправка, приём отчётов о доставке и регистрация имён отправителей.

| Термин | В коде | Определение |
|---|---|---|
| Провайдер | `Provider` | Внешний SMS-агрегатор или прямое подключение к оператору, через которое уходит сообщение |
| Оператор | `Carrier` | Мобильный оператор получателя (МТС, Билайн, МегаФон, T2) |
| Маршрут | `Route` | Правило «оператор → провайдер, порядок резервных провайдеров» |
| Попытка отправки | `DeliveryAttempt` | Одна передача сообщения одному провайдеру. У сообщения их может быть несколько (failover, US-18) |
| Отчёт о доставке | `DeliveryReport` (DLR) | Ответ оператора о судьбе сообщения: доставлено, не доставлено, отклонено |
| Имя отправителя | `SenderName` | Буквенное имя (`MyShop`), зарегистрированное у операторов. Статусы: `pending`, `approved`, `declined` |

### 4. Биллинг (Billing)
Деньги: баланс, резервы, списания, пополнения, документы.

| Термин | В коде | Определение |
|---|---|---|
| Баланс | `Balance` | Доступные деньги аккаунта = пополнения − списания − активные резервы |
| Резерв | `Hold` | Деньги, временно заблокированные под принятое сообщение до финального статуса |
| Списание | `Charge` | Окончательное снятие денег за сообщение (`delivered` или `undelivered`) |
| Снятие резерва | `Release` | Возврат резерва на баланс, если оператор отклонил сообщение (`rejected`) |
| Пополнение | `TopUp` | Поступление денег картой или по счёту |
| Тариф | `Tariff` | Цена одного сегмента для аккаунта (базово 3,20 ₽) |
| Тестовая квота | `TestQuota` | Бесплатные тестовые SMS (50 при регистрации). Это не деньги и баланс они не трогают |

### 5. Вебхуки (Webhooks)
Сообщает серверу клиента, что что-то произошло. Это MLP (US-05), но границу закладываем сразу.

| Термин | В коде | Определение |
|---|---|---|
| Эндпоинт | `WebhookEndpoint` | URL клиента, куда мы шлём события, и секрет для подписи |
| Событие | `Event` | Факт из прошлого: `message.delivered`, `balance.low` |
| Отправка вебхука | `WebhookDelivery` | Одна попытка POST-запроса на эндпоинт клиента |
| Подпись | `Signature` | HMAC-SHA256 тела запроса. По ней клиент проверяет, что вебхук от нас |
| Повтор | `Retry` | Повторная отправка при ответе не 2xx: 1 мин, 5 мин, 30 мин, 2 ч, 6 ч |

### Почему именно такие границы — одно слово, разные смыслы
- **«Статус»**: в Сообщениях это судьба SMS для клиента (`delivered`), в Доставке — результат одной попытки у одного провайдера, в Вебхуках — дошёл ли наш POST до клиента. Если свалить всё в один `Status`, получится God Object.
- **«Доставка»**: в контексте 3 — доставка SMS абоненту, в контексте 5 — доставка вебхука серверу клиента. Поэтому в коде они называются по-разному: `DeliveryAttempt` и `WebhookDelivery`.
- **«Отправитель»**: это не аккаунт, а именно `SenderName`. Слово «клиент» в коде не используется вообще: только `Account` (наш клиент) и `Recipient` (получатель SMS).

## 2. BDD: критический путь MVP «Первое SMS»

**Почему этот путь:** главная метрика — время до первого SMS (TTFS < 10 мин), а главная гипотеза из ДЗ 2 — что разработчики придут ради быстрой интеграции. Если этот путь сломан, продукта нет. Путь покрывает US-01, US-02, US-04 и US-09.

### Сценарий 1 (успех): первое SMS доставлено

```gherkin
Функция: Первое SMS после регистрации

  Сценарий: Разработчик отправляет первое тестовое SMS на свой номер
    Дано разработчик зарегистрировался и подтвердил номер +79991234567
    И он находится на экране «Быстрый старт»
    И у аккаунта 50 тестовых SMS и баланс 0,00 ₽
    И на экране показан тестовый ключ sk_test_…a7f2
    Когда разработчик нажимает «Отправить первое SMS» с текстом «Привет от SMSGate!»
    Тогда API отвечает 202 Accepted со статусом «queued» и 1 сегментом
    И в блоке «Последние сообщения» появляется строка со статусом «В очереди»
    И в течение 30 секунд статус меняется на «Доставлено» с зелёной галочкой
    И счётчик тестовых SMS показывает 49
    И баланс остаётся 0,00 ₽
    И появляется плашка «Первое SMS за 4 мин 12 с. Готовы к боевым отправкам? Пополнить баланс»
```

### Сценарий 2 (отказ): тестовым ключом на чужой номер

```gherkin
  Сценарий: Разработчик пробует отправить тестовое SMS на неподтверждённый номер
    Дано разработчик подтвердил номер +79991234567
    И у аккаунта 49 тестовых SMS и баланс 0,00 ₽
    Когда разработчик отправляет POST /v1/messages с тестовым ключом на номер +79160000000
    Тогда API отвечает 403 с кодом ошибки «test_key_restricted»
    И в ответе есть подсказка «Тестовый ключ отправляет SMS только на подтверждённый номер +7999***4567»
    И в ответе есть ссылка docs_url на раздел «Тестовый режим»
    И сообщение не создаётся и в журнале не появляется
    И счётчик тестовых SMS остаётся 49
```

### Дополнительно: повтор запроса (идемпотентность — наше УТП)

```gherkin
  Сценарий: Повтор запроса после таймаута не создаёт второе SMS
    Дано разработчик отправил POST /v1/messages с Idempotency-Key «order-1042-otp»
    И получил ответ 202 с id «msg_01JC8Z3K»
    Когда он повторяет тот же запрос с тем же Idempotency-Key через 10 секунд
    Тогда API отвечает 202 с тем же id «msg_01JC8Z3K»
    И в ответе есть заголовок «Idempotent-Replayed: true»
    И получатель получает ровно одно SMS
    И с аккаунта списана оплата ровно за одно SMS
```

## 4. API-First: JSON-контракты

Общие правила для всех ручек:
- базовый URL `https://api.smsgate.ru/v1`;
- авторизация заголовком `Authorization: Bearer <api_key>`;
- даты в ISO 8601 UTC;
- **деньги передаются строкой** (`"3.20"`), а не числом, чтобы не терять копейки на float;
- id с префиксом типа (`msg_…`, `req_…`): по id сразу видно, что это за объект;
- все ошибки в одном формате (US-09).

Полный контракт — в [api/openapi.yaml](api/openapi.yaml).

### Ручка 1. `POST /v1/messages` — отправить SMS (US-02, US-03)

**Запрос**

```http
POST /v1/messages
Authorization: Bearer <YOUR_API_KEY>
Idempotency-Key: order-1042-otp
Content-Type: application/json
```

```json
{
  "to": "+79991234567",
  "text": "Ваш код подтверждения: 4821",
  "sender": "MyShop",
  "client_ref": "order-1042"
}
```

| Поле | Тип | Обяз. | Описание |
|---|---|---|---|
| `to` | string | да | Мобильный номер РФ. Принимаются `+79…`, `79…`, `89…`, ответ всегда в E.164 |
| `text` | string | да | От 1 символа до 6 сегментов |
| `sender` | string | нет | Одобренное имя отправителя. Если не указано, используется общее имя сервиса |
| `client_ref` | string | нет | Ваш id для связи с заказом, до 64 символов. Возвращается в ответах и вебхуках |

**Ответ `202 Accepted`**

```json
{
  "id": "msg_01JC8Z3KQ7V4M2",
  "status": "queued",
  "to": "+79991234567",
  "sender": "MyShop",
  "client_ref": "order-1042",
  "segments": 1,
  "encoding": "UCS2",
  "price": { "amount": "3.20", "currency": "RUB" },
  "mode": "live",
  "created_at": "2026-11-03T11:03:21.104Z"
}
```

Заголовки ответа: `X-Request-Id: req_7Hc2Lw9`. При повторе с тем же ключом добавляется `Idempotent-Replayed: true`.

**Ошибки**

```json
{
  "error": {
    "code": "insufficient_funds",
    "message": "Недостаточно средств: нужно 3.20 ₽, доступно 1.10 ₽",
    "docs_url": "https://docs.smsgate.ru/errors#insufficient_funds",
    "request_id": "req_7Hc2Lw9"
  }
}
```

| HTTP | `code` | Когда |
|---|---|---|
| 401 | `unauthorized` | Ключ неверный или отозван |
| 402 | `insufficient_funds` | Не хватает денег на все сегменты |
| 403 | `test_key_restricted` | Тестовый ключ, а номер не подтверждён |
| 409 | `idempotency_key_reused` | Тот же `Idempotency-Key`, но другое тело запроса |
| 422 | `invalid_phone` | Номер не мобильный РФ |
| 422 | `text_too_long` | Больше 6 сегментов |
| 422 | `sender_not_approved` | Имя отправителя не одобрено |
| 429 | `rate_limited` | Больше 50 запросов в секунду. Смотрите заголовок `Retry-After` |


```json
  "to": "+79991234567",
  "sender": "MyShop",
  "client_ref": "order-1042",
  "segments": 1,
  "encoding": "UCS2",
  "price": { "amount": "3.20", "currency": "RUB" },
  "charged": true,
  "mode": "live",
  "carrier": "megafon",
  "error": null,
  "status_history": [
    { "status": "queued",    "at": "2026-11-03T11:03:21.104Z" },
    { "status": "sent",      "at": "2026-11-03T11:03:21.890Z" },
    { "status": "delivered", "at": "2026-11-03T11:03:25.412Z" }

```

**Ответ `200 OK` (оператор отклонил, деньги вернулись)**

```json
{
  "id": "msg_01JC8Z9WD2P1XR",
  "status": "rejected",
  "price": { "amount": "3.20", "currency": "RUB" },
  "charged": false,
  "error": {
    "code": "carrier_rejected",
    "message": "Оператор отклонил сообщение: имя отправителя не зарегистрировано у T2"
```
